title: Local-first sync
description: The versioned change log, idempotent pushes, tombstones, cursors, and conflict snapshots.

Lattice treats the device as the primary read/write surface and the server as a sync and collaboration authority.

## Local store

Each user gets a Dexie database named `lattice-${userId}` with tables for:

`workspaces`, `members`, `notebooks`, `pages`, `pageDocuments`, `canvases`, `nodes`, `edges`, `tags`, `pageTags`, `captures`, `templates`, `decks`, `flashcards`, `reviewLogs`, `comments`, `attachments`, `conflicts`, `outbox`, `meta`.

A write does three things atomically:

1. Updates the local table.
2. Derives dependent records (plain text, page-link edges, graph nodes).
3. Enqueues an outbox op keyed by `entity:entityId`.

The editor autosaves with a debounce and flushes on blur and teardown.

## Server change log

The sync stream is not ordered by wall-clock timestamps. Each workspace has a monotonic `syncVersion`.

```text
BEGIN
  apply op(s)
  UPDATE workspace SET syncVersion = syncVersion + 1
  INSERT sync_change(version, entity, entityId, op, data) for each changed row
COMMIT
```

Clients pull with a composite cursor `(version, id)` and apply changes idempotently. Deletes are soft deletes and appear in the stream as tombstones, so removed content cannot resurrect.

## Push contract

```ts
type SyncOp = {
  opId: string;        // client-generated, unique, retry-safe
  entity: SyncEntity;  // page, pageDocument, canvas, node, ...
  entityId: string;
  op: "UPSERT" | "DELETE";
  baseRev?: number;    // required for document revisions
  payload: Record<string, unknown>;
};
```

Inside one transaction the server:

1. Validates workspace membership and resource access.
2. Skips duplicate `opId`s using `sync_op` (idempotency).
3. Checks `baseRev` for `pageDocument` and `canvas`.
4. Applies the mutation, scoped by workspace.
5. Appends change-log rows at one new workspace version.
6. Returns accepted revisions, conflicts, and the new version.

## Conflicts

If a page body has changed remotely since the client's `baseRev`:

- The server writes the current remote document into `PageVersion`.
- It records a `SyncConflict` with both payloads.
- It rejects the push with a conflict result.
- The client keeps its local document and shows a compare dialog.

Nothing is silently overwritten. The user can keep the local version (server snapshots the remote first) or keep the server version (local reader updates immediately).

### Writes during a live session

Live peers converge through the CRDT, so their JSON snapshots arrive with stale
revisions by design; the server must accept those or co-editing would stop at
every keystroke. Document ops therefore carry an **origin** (`session` or
`write`), and only session snapshots get that exemption:

- `session` — sent by the editor's live persist path. A stale revision is
  accepted and applied.
- `write` — everything else: accepting a suggestion, restoring a version,
  Markdown-mode saves, imports, the API's `page.saveDocument`, plugin writes.
  These are revision-checked like any other entity, so a stale one becomes a
  `SyncConflict` instead of silently losing to a peer's older body.

The change log keeps the origin, so clients can attribute the revision they
received.

Two companion rules close the rest of the gap:

- A live editor will not persist when the local document advanced from a
  `write` it did not make. It stops saving, warns that the note changed outside
  the session, and offers **Reload note** instead of putting the older body
  back.
- **Reload note** calls `sync.resetCollab`, which drops the stored CRDT and any
  live room for that page. Peers reconnect against a fresh room and seed from
  the stored document, so the newer body is what everyone continues from.

What is still not attempted: merging an out-of-band write into a live CRDT.
Today the session is reset rather than merged, which costs a reconnect but never
picks a silent winner.

## Multi-tab and offline behavior

- A Web Locks leader (`lattice-sync-<userId>`) owns push/pull; other tabs read the same IndexedDB.
- Online/offline and visibility events drive retries.
- The sync chip exposes `synced`, `syncing`, `offline`, `queued`, and `conflict` states.
- Initial boot calls `workspace.ensure`, then a snapshot, then incremental pulls.
- `sync.snapshot` is also the repair path if a device's cursor is older than the retained change log.

### Snapshot paging

A snapshot arrives in pages, not one response: collections in a fixed order
(workspace, members, notebooks, pages, bodies, canvases, graph, tags, captures,
templates, decks, cards, comments, attachments, suggestions, object types), each
paged by id with a keyset cursor (`pageSize` 500 by default, 2,000 max). The
first page pins the workspace's sync version and every page reports it; the
client stores nothing until `done`, then applies the assembled payload and sets
its cursor to that version. Anything that changes mid-download has a later
change-log version, so the following pull reconciles it. A page set is also the
repair path when a device's cursor is older than the retained change log.
Edge visibility is checked against just the endpoints on the current page, not
every node in the workspace.

## Access filtering

Pull and snapshot responses filter private pages and dependent nodes, edges, comments, attachments, and cards for non-admin members. Admins see the workspace for governance; creators always see their own private content.

## Live co-editing

Page bodies are bound to a Yjs document while a page is open, relayed by the server on a per-page WebSocket room. Concurrent edits merge in the CRDT and each peer persists the converged JSON, so the revision machinery below stays the safety net for offline and single-writer cases rather than a source of conflicts during a live session.

The CRDT is a live layer with its own durability, not the system of record: the room is in memory, the document is persisted per page and flushed when the last peer leaves, and the stored page document remains the system of record. Writing a page outside a live session — a version restore, a Markdown-mode save, an import — drops the stored CRDT, because that write is newer than anything the CRDT knows about.
