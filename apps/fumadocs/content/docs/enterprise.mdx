Lattice runs inside your own deployment, so workspace data lives on infrastructure
you control. This page covers the controls an organization needs on top of that,
and it is deliberately honest about what is shipped, what is next, and what is
not attempted.

## Shipped: SCIM 2.0 provisioning

**Settings → Members → Provisioning (SCIM)** issues bearer tokens and shows the
base URL to give an identity provider:

```text
https://your-lattice.example/scim/v2
Authorization: Bearer scim_…
```

Each token is bound to one workspace, stored as a SHA-256 hash, shown once, and
revocable independently — issue one per IdP so revoking one does not disturb the
other. At most five active tokens per workspace.

### Endpoints

| Method | Path | Notes |
| --- | --- | --- |
| `GET` | `/ServiceProviderConfig` | Advertises PATCH and filter support. |
| `GET` | `/Schemas`, `/ResourceTypes` | Discovery for the admin console. |
| `GET` | `/Users` | Filter with `userName eq "…"`, `externalId eq "…"`, or `displayName eq "…"`; `startIndex` / `count` (max 100). |
| `GET` | `/Users/:id` | |
| `POST` | `/Users` | Creates the account if the email is new, then the membership. `409` with `scimType: uniqueness` if already provisioned. |
| `PUT` | `/Users/:id` | Replaces email, display name, `active`, `externalId`, and role. |
| `PATCH` | `/Users/:id` | Supports `replace active`, `name`, `externalId`, and `roles`. |
| `DELETE` | `/Users/:id` | Soft-deletes the membership (`SUSPENDED`) and logs the deprovision. |
| `GET`/`POST` | `/Groups` | Group membership assigns the group's role. |
| `GET`/`PATCH`/`DELETE` | `/Groups/:id` | `add`/`remove` member operations via the standard `members` path. |

Every read is scoped to the token's workspace, and every write goes through the
change log and the audit log, so provisioned changes reach every device and show
up in **Settings → Audit log**.

### Role mapping

- `roles[].value` or group names containing `admin` → `ADMIN`
- `editor`, `member`, or `write` → `EDITOR`
- `viewer`, `read`, or `guest` → `VIEWER`
- Anything mentioning `owner` is rejected: ownership is transferred in the app.

Group names carry the role (`lattice-admins`, `design-viewers`); a custom
`urn:lattice:scim:1.0:Group` attribute `{ "role": "viewer" }` wins when present.
Adding a member to a group applies the role; removing them leaves the role in
place so a mistaken removal does not quietly downgrade someone.

### What it does not do

- No passwords are accepted. Provisioned accounts sign in through whatever
  method the deployment offers (SSO once it ships, or a password reset).
- No `externalId` uniqueness constraint beyond `(workspace, externalId)` lookups;
  two members can share one if the IdP sends it.
- No bulk operations (`/Bulk`), sorting, or ETags. The discovery document says so.

## Shipped: SSO (OIDC)

**Settings → Members → Single sign-on (OIDC)** stores one connection per
workspace. Register this redirect URI at the identity provider:

```text
https://your-lattice.example/api/auth/sso/callback
```

Then save the issuer URL, client id, client secret, and the email domains that
should route to this workspace. Authorization Code + PKCE with a nonce, an
issuer/audience/`nonce`-checked ID token, and a JWKS from the issuer's discovery
document. Only `https` issuers are accepted, except `localhost` so a provider can
be run locally.

Sign-in happens at `/api/auth/sso/start?workspace=<slug>&redirect=/app`:

1. The login page asks for a work email, resolves its domain to a workspace
   (`sso.discover` — it returns only a slug), and starts the flow.
2. The callback exchanges the code server-side, so the client secret never
   reaches a browser, and verifies the ID token.
3. The identity must be an **active, provisioned member** of that workspace;
   otherwise the browser lands on the login page with
   `?sso_error=not_provisioned`. Provisioning is SCIM's or an invite's job.
4. The session is created through better-auth's own adapter, so expiry,
   revocation, and the device list behave exactly like a password sign-in.
5. The redirect back is resolved against an allow-list; `//evil.example.com`
   falls back to `/app`.

Details worth knowing:

- **Unverified email is refused.** `email_verified` must be true in the ID token
  or userinfo; a provider that does not assert it cannot sign anyone in.
- **The client secret is encrypted at rest** with AES-256-GCM under a key
  derived from the deployment secret, so a database dump alone cannot be used
  at the provider.
- **SAML is not implemented.** OIDC covers Okta, Entra ID, Google, Auth0, and
  Keycloak; a SAML-only IdP needs a SAML library and an XML-signature review.
- The flow is verified end-to-end against a local test provider
  (`apps/server/src/fake-idp.ts`): start → authorize → callback → session, plus
  the unknown-workspace, replayed-state, redirect, and unprovisioned guards.

## Shipped: legal hold and export on demand

**Settings → Legal** places a hold on the whole workspace, a notebook, or a
page. A hold outranks retention, so the scheduled purge skips every covered row
it would otherwise remove — pages, comments, attachments, cards, decks, canvases,
and graph nodes and edges — and a workspace hold stops the purge for that
workspace entirely. Releasing a hold only affects future purges: nothing is
deleted at release time, and the next purge can remove the content if it is still
expired. (Page bodies and saved versions are not deleted by the purge path at
all today, so they survive regardless of a hold.)

Coverage is deliberately explicit:

- **Workspace** — nothing in the workspace is purged.
- **Notebook** — the notebook, its pages (and their comments, attachments, and
  cards), its canvases, and its decks survive. A page's notebook is its direct
  parent, so a page moved out of the notebook is no longer covered.
- **Page** — that page and the rows attached to it survive.

**Download legal export** builds the bundle server-side and writes an audit
entry (`legal_export.created`) with the record counts. It includes soft-deleted
rows and the audit log on purpose, and never includes SSO client secrets, webhook
signing secrets, or ingest/SCIM token hashes. Lists are capped at 5,000 pages,
5,000 versions, 10,000 comments, and 5,000 audit entries; the bundle records
which lists were truncated.

Verified against the purge itself: with a page hold only that page survived; with
a notebook hold its page, deck, card, and notebook survived while the rest were
removed; a workspace hold purged nothing; and releasing the hold let the next
purge remove everything.

## Next: BYOK for AI

Workspace-owned provider credentials, encrypted at rest with a server key and
masked on read, so an organization can point Lattice at its own AI account
without editing deployment env vars.

## Not attempted: end-to-end encryption

E2EE is a redesign, not a feature switch: it would move page bodies out of
server reach, which collides with server-side search, embeddings, AI retrieval,
share links, and the webhook stream. Doing it credibly means client-held keys,
per-member key envelopes, rotation and recovery, and deciding explicitly which
features go dark when keys are present. Lattice does not claim it, and the
[security page](/docs/security) says the same.

## Deployment controls

- One database and upload directory per deployment; workspace data is
  workspace-scoped in every query.
- Hashed share, invite, ingest, and SCIM tokens; per-IP rate limits with separate
  buckets for auth, ingest, SCIM, share, and the API.
- Audit log with CSV export, device list with revocation, workspace-chosen trash
  retention, and a scheduled purge.
- AI is optional and configured per deployment; user input never becomes an
  outbound endpoint.
