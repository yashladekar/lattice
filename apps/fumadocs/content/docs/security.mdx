Security is enforced at the API boundary and mirrored in the UI, not trusted from the client.

## Authentication

Better Auth handles email/password sessions and Expo session forwarding. Cookies are `HttpOnly`, `SameSite=None`, `Secure` for cross-origin web and desktop flows. Native stores the session in SecureStore and forwards it explicitly.

## Workspace scoping

Every workspace-scoped procedure resolves membership server-side using the session user and `x-workspace-id`. Handlers derive the workspace from that verified membership; payload workspace ids are not trusted.

For sync writes:

- Existing entity ids are checked against the workspace.
- Parent chains (notebook, parent page, canvas) are validated.
- Page moves reject cycles.
- Cross-tenant id collisions are rejected, not upserted.

## Authorization

Role rank gates mutations. Page access additionally considers creator, visibility, and explicit resource permissions.

- Private page content is removed from pull/snapshot for other members.
- Explicitly shared pages require a matching resource permission.
- Guests cannot see workspace-wide resources.

## Share tokens

- 32 random bytes, base64url encoded.
- SHA-256 hash stored in Postgres.
- Expiry and revocation checked on every public request.
- Public payloads never include sibling pages, workspace member data, or private linked titles.
- `Referrer-Policy: no-referrer` is set on the public share layout.

## Rate limiting

Express applies a per-IP budget with separate buckets for auth (60/min), email ingest (30/min), SCIM (240/min), public share lookups (90/min), and everything else (600/min). Counters are fixed windows in this process: expired buckets are dropped as they are seen and a sweep clears the rest every minute. Running more than one API instance multiplies every limit, so scale out with a shared limiter or a single instance in front.

## Uploads

`POST /uploads` requires a valid session, accepts one raw file body up to 25 MB, writes to a server-owned directory with a generated filename, and serves only the file URL. Images and audio/video are served inline (they need cross-origin reads for canvas and playback); every other type is served as a download with `X-Content-Type-Options: nosniff` and a sandbox CSP, so an uploaded HTML or SVG file cannot run code on the API origin.

### PDF text extraction and OCR

PDF captures can be extracted from the inbox. The API reads the stored file, extracts selectable text with PDF.js (`unpdf`), and appends it to the capture through the sync change log. Files above 25 MB are refused.

When a PDF has no text layer, or for images, the browser does the OCR instead: the stored file is downloaded with the session cookie, pages are rasterized locally with `pdfjs-dist`, and text is recognized with `tesseract.js`. Nothing is uploaded for OCR and no provider is required — the trade-off is that the first run downloads the OCR engine and English model from jsDelivr unless `NEXT_PUBLIC_TESSERACT_CDN` points at a self-hosted mirror. Up to 15 pages are read per file, and the recognized text lands through the normal capture change log. Audio captures can additionally be transcribed by the server's provider when one is configured.

## Plugins

Plugins run in a worker with the ambient network, storage, and indexing APIs removed before their code loads. Every callable method maps to a capability in the domain (`PLUGIN_METHODS`), and the host answers a call only when the record granted that capability — the worker never decides what it may do.

Manifest-declared **blocks** and **canvasTools** only describe where a plugin can be invoked. A block's node stores what the plugin returned, so the output is ordinary document content: it syncs, versions, and exports like any other block. Markdown output is converted through the same importer used for GitHub imports and then stripped of non-http/mailto/tel link and image targets (`stripUnsafeHrefs`). The passive run context (`ctx.input()`, `ctx.canvas()`, `ctx.tool()`) is data the host chooses to hand over — canvas data only when `graph:read` is granted — and never widens what the plugin can call.

## Retention

Deletes are soft deletes. Each workspace can set a trash window (30/90/180/365 days, or keep forever) in Settings → General. A scheduled server job then permanently removes soft-deleted rows older than that window and appends tombstone changes, so clients converge on the same result. There is intentionally no manual purge button; an instant purge needs its own op semantic to stay consistent with local-first clients.

**Legal holds outrank retention.** A workspace, notebook, or page hold (Settings → Legal) makes the purge skip every covered row it would otherwise remove — pages, comments, attachments, cards, decks, canvases, and graph nodes and edges — and a workspace hold stops the purge for that workspace entirely. Releasing a hold only affects future purges; nothing is deleted at release time. Page bodies and saved versions are removed with the page through the schema's cascade. **Settings → Legal → Download legal export** produces an audited JSON bundle that includes soft-deleted rows on purpose and never includes credentials or token hashes.

## Explicitly deferred

The schema and service boundaries include hooks for, but this release does not claim:

- end-to-end encryption,
- a full audit-grade compliance program (certification, evidence collection, retention attestations).

SCIM provisioning, OIDC single sign-on, legal hold, and export on demand are implemented; see [Enterprise](/docs/enterprise). The two items above are product-level programs, not UI states. See [Roadmap](/docs/roadmap).
