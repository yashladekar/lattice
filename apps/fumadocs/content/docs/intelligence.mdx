The intelligence layer is optional. Lattice is useful without any model provider.

## Modes

| Mode | Behavior |
| --- | --- |
| ChatGPT plan | Server calls the OpenAI Responses API with the signed-in member's own ChatGPT plan |
| Provider | Server calls an OpenAI-compatible chat endpoint with retrieved note context |
| Local | Token-overlap retrieval from the workspace, with passages and citations |

The UI labels responses as **ChatGPT plan**, the configured model, or **Local mode**. It never presents heuristic retrieval as a synthesized answer.

## Configuration

The deployment can configure a provider through environment variables:

```dotenv
AI_BASE_URL=https://api.openai.com/v1
AI_API_KEY=...
AI_MODEL=gpt-4.1-mini
```

A workspace can instead store its own credentials in **Settings → Intelligence →
Workspace AI credentials** (base URL, key, chat model, embedding model,
transcription model). That is what bring-your-own-key means here:

- The workspace key **wins over the deployment configuration**; removing it falls
  back to the deployment provider, and with neither, AI answers use local
  retrieval.
- The key is encrypted with AES-256-GCM under a key derived from the deployment
  secret and is only ever returned masked (`••••wxyz`). It is never written to the
  audit log.
- The base URL is admin-set, which is a deliberate capability: an organization can
  point at its own gateway. It is validated as https (http only for localhost),
  with no embedded credentials, query, or fragment.
- A key that cannot be decrypted (for example after rotating the deployment
  secret) falls back to the deployment configuration instead of breaking AI; the
  settings panel shows which source is in effect.

In both modes the provider is an OpenAI-compatible endpoint: the server sends
chat, embedding, and transcription requests itself, and no note content reaches a
provider until a member asks a question or an editor builds the semantic index.

## ChatGPT plan

Instead of an API key, each member can sign in with their own ChatGPT account and
run AI requests against their Plus or Pro plan. This is OpenAI's
[Sign in with ChatGPT](https://developers.openai.com/siwc/quickstart) open-source
token-sharing flow.

### Connecting

1. **Settings → Intelligence → ChatGPT plan → Continue with ChatGPT.**
2. Your system browser opens OpenAI's consent screen. Approve the request.
3. The browser returns to the loopback callback
   (`http://127.0.0.1:1455/auth/callback`), Lattice exchanges the code, validates
   the ID token, and stores the tokens.

Two constraints follow from OpenAI's contract, not from Lattice:

- **The sign-in only works when the Lattice server runs on the same machine as
  the browser** — `pnpm dev`, a local `docker compose up`, or the desktop build.
  OpenAI only accepts a `127.0.0.1` callback, and `127.0.0.1` is the browser's
  machine. On a remote server, use **Export credential** / **Import credential**
  to transfer a session, following OpenAI's self-hosted VM guidance.
- **Plan usage covers `POST /v1/responses` only.** No embeddings, no audio
  transcription, no `temperature` or `max_output_tokens`. The semantic index and
  transcription therefore keep using a workspace or deployment API key, and say
  so plainly when neither exists.

### Precedence

The preferred chat backend is per member, per workspace:

| Preference | Order |
| --- | --- |
| Automatic (default) | ChatGPT plan → workspace key → deployment key |
| ChatGPT plan | ChatGPT plan only, with an explicit notice if unavailable |
| Workspace provider | Workspace key only |
| Deployment provider | `AI_API_KEY` only |

Embeddings and transcription always come from whichever API key is configured;
they never route through the ChatGPT plan. A failed plan request is never retried
on another billing path — you get the error and a local answer instead.

### Credentials

- Access tokens last one hour; refresh tokens last 30 days and rotate on every
  refresh. Refreshes are serialized per credential so two requests cannot race a
  rotating token.
- Access, refresh, and ID tokens are encrypted with AES-256-GCM under a
  purpose-separated key (`chatgpt`). They never reach the browser, are never
  logged — including the authorization URL, which carries the retained
  `id_token_hint` — and are never written to a client-side store.
- **Disconnect** revokes the refresh token at OpenAI's revocation endpoint before
  deleting the row. If revocation cannot be confirmed, Lattice says so; you can
  also disconnect from ChatGPT settings.
- Usage and limits live at [chatgpt.com/settings/usage](https://chatgpt.com/settings/usage).
  Plan limits are shared across every app that uses your ChatGPT plan.

## Plan mode (experimental)

Behind `AI_AGENT_ENABLED=true`, the Ask panel grows a **Plan** toggle. With it on,
the assistant can read pages, follow graph relations, and propose a concrete set
of changes instead of only writing an answer.

It is off by default. Set `AI_AGENT_ENABLED=false` (or remove it) and restart to
hide the whole surface; the code stays in place and nothing else is affected.

### What it can propose

| Op | Effect |
| --- | --- |
| Append / insert / replace blocks | Edits one page's body |
| Replace page body | Rewrites a whole page — for repair or a restructure |
| Create page | A new page from Markdown |
| Create whiteboard | A mind map, flow, or concept map built from an outline |
| Add to whiteboard | A new cluster placed below what is already on a board |
| Link pages | A typed graph relation, marked `origin: AI` |
| Create flashcards | Cards in the daily-review deck |

There is **no delete op**. Destructive changes are not representable, so the
worst a confused model can do is add something you then discard.

### Writing from general knowledge

Plan mode is the authoring surface. Ask it for notes on a topic and it drafts
them from its own knowledge — an empty workspace is the normal starting point,
not a blocker. Such a page opens with a plain line saying it was drafted from
general knowledge rather than derived from your workspace, so provenance is
never ambiguous. For a broad subject it proposes a few focused pages
(fundamentals first) rather than one enormous one.

Pages a plan creates can be connected to each other in that same plan. Each
`create_page` may carry an alias, and later ops use it, so a beginner-to-advanced
set arrives already linked instead of as a pile of loose notes. Aliases exist
only inside one plan; they are resolved to real page ids as the plan is applied.

Diagrams are part of the draft: a ```mermaid fence inside a page becomes a
rendered Mermaid diagram rather than a code block, which is how system-design
notes get their request paths, sequence diagrams and data models. A fence
Mermaid would not understand stays a code block instead of an error box. Images
are not available — a model-supplied image URL is exactly the kind of thing the
block allowlist exists to stop.

A plan can also create a whiteboard: mind map, flow, or concept map. The model
supplies only an outline and a layout name; positions come from the same layout
code the mind-map action uses, so elements never overlap. It can list and read
existing whiteboards too, and prefers adding to one you already drew over making
a duplicate — the new cluster is placed below the existing content, and nothing
you made is moved or removed.

Additions are additive. The assistant cannot edit or delete elements on a
whiteboard, and it cannot rearrange one.

Plain **Ask** answers from your notes and cites them. When they do not cover the
question it says so in one line, then continues from general knowledge under a
"From general knowledge" heading with no citations — so you always know which
part is which. Use Ask to interrogate what you have or to ask a general
question, and Plan mode when you want pages created.

### How a change is applied

The server only ever reads. It runs a bounded loop (6 model turns, 12 ops) over
its own tools — `search_pages`, `read_page`, `related_pages`, `graph_neighbors`,
`list_pages` — and returns a plan. The plan is rendered as a card with a preview
per change, and **nothing is written until you press Apply**.

Applying happens on your device, and a snapshot is saved first (`Before AI edit`,
visible in the page timeline). Then:

- **With the page open in the editor**, the blocks are applied through that
  editor's own transaction. A live collaborative session sees the change
  immediately and every connected device receives it — no reload.
- **With the page closed**, the document is written through the normal local
  repository and sync op instead, and the edit is there when you next open it.

### Why it works this way

Two reasons, both structural:

- A server-side write to a page someone has open loses to that editor's next
  save — the collaboration layer deliberately does not drop a live room for an
  out-of-band write. Applying on the client removes the race entirely.
- Tool output is untrusted text. Emailed captures, pasted pages, and imports all
  reach the model. The prompt tells the model that note content is data, but the
  real boundary is the allowlist (no embeds, no images, no executable blocks),
  the per-page access check on every proposed op, the op caps, and the human
  Apply click.

Plan mode is available on web and desktop. The native assistant can use a
connected ChatGPT plan or API key for answers, but not plan mode.

## Conversations

Ask keeps a history. Every turn is stored per member and per workspace, and the
clock button in the panel lists recent conversations so you can pick one back up
where it stopped. Reopening a conversation also restores any plan it proposed,
so an old card can still be reviewed and applied.

History lives in the database, not the browser — it survives reloads and follows
the account across devices that use the same server.

## Retrieval

1. Resolve pages visible to the requesting member (private pages excluded unless allowed).
2. Rank title, body, and scope by token relevance, using the provider's semantic index when one is built and token ranking otherwise.
3. Limit the context window and keep source excerpts.
4. Ask the provider to cite sources by index.
5. Return the answer with structured `{ pageId, title, excerpt }` citations.

## Local vectors

Client-side retrieval does not depend on a provider. Every document the app holds
locally is also indexed with
**local vectors** (`@notes-learning/domain`, `local-vectors.ts`): text is
tokenized with stopword removal, light plural/gerund folding, and phrase
bigrams; terms are weighted by sublinear term frequency and inverse document
frequency, hashed into 512 dimensions, and L2-normalized so a dot product is
cosine similarity. Search, the command palette, and the plugin `search` API rank
with it (see [Search](/docs/search)).

Be clear about what this is: a deterministic lexical-vector index, not a neural
embedding. It closes the gap that hurts token search most — "habits" finds a
note that says "habit", word order matters through bigrams, rarer terms count
for more — and it runs identically offline, in a worker, and on a phone, with no
download and no network. The server-side Ask path keeps using provider embeddings
when configured, and plain token ranking when not.

## Capabilities

- Ask across a workspace or a specific page scope.
- Summarize a page.
- Explain a concept with a concrete example.
- Compare a page with its related notes, based on shared vocabulary.
- Suggest additional examples.
- Find missing connections using shared vocabulary + graph structure.
- Generate flashcards from a page.
- Generate a mind-map outline.
- Identify likely outdated notes (age or unresolved TODO) and open them from the
  result list.
- Surface knowledge gaps from dependency edges and card mastery.

Editor results render citations as clickable chips that open the source page,
and every "apply" action (cards, mind map, connection) stays explicit. A
generated mind map is previewed as a canvas thumbnail before **Create
whiteboard** turns it into a real whiteboard.

## Graph queries

Some questions are better answered from the graph than from a language model.
The Ask panel recognizes them and answers **locally, with citations, even
offline**:

- “What is connected to *Spaced repetition*?” — lists in/out relations with
  their types.
- “How are *X* and *Y* related?” — finds the shortest path and shows each hop.
- “Which notes are orphans?” — lists nodes with no connections.
- “What are the most connected notes?” — ranks hubs by degree.

Ambiguous names return the candidate list instead of guessing. Anything that is
not a graph question falls through to the server retrieval/provider path.

## Semantic index

With an OpenAI-compatible provider configured, **Settings → Intelligence → Semantic index**
embeds each page and stores the vectors in Postgres. Ask then embeds the question
and ranks pages by cosine similarity before building the context for the model.
Without an index, or if the provider cannot produce embeddings, retrieval falls
back to token overlap.

- The embeddings model comes from `AI_EMBEDDING_MODEL` (default
  `text-embedding-3-small`).
- The index is per workspace and rebuilds on demand; rebuild after large imports
  or a model change.
- Vectors are stored as JSON, so no Postgres extension is required at this scale.
- Pages the requester cannot read are excluded before ranking.

## Guardrails

- AI can propose; it cannot silently write. Applying cards, connections, or pages is a user action.
- AI-created records carry `aiGenerated` where the schema supports it.
- Answers include source references; unsupported claims should be treated as untrusted.
- The Ask panel is separate from the editor; it does not rewrite content in place.
