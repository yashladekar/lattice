### Why a static web app

`apps/web` uses `output: "export"` and query-param routing under `/app`. That makes the same build usable as:

- a browser application,
- an installable PWA,
- a Tauri desktop application,
- a static bundle for an internal self-hosted portal.

The API is separate. Runtime configuration lives in `public/config.js`, so a desktop bundle can point at a self-hosted API without rebuilding.

### Shared domain package

`packages/domain` is pure TypeScript. It contains:

- Serialized entity types used by local storage and transport.
- Zod contracts for sync operations and API inputs.
- Permission helpers and role ranking.
- TipTap JSON extraction: plain text, page links, tags, outlines, Markdown.
- Graph derivation, degree, clusters, orphans, learning paths.
- SM-2 scheduling, flashcard generation, quiz generation.
- Canvas document types, templates, mind map and diagram builders.
- Search ranking and related-note suggestions.

Both the API and clients share this package, so a relation type or card schedule cannot drift between platforms.

### Request flow

1. The client sends `x-workspace-id` plus its Better Auth cookie / bearer token.
2. `workspaceProcedure` verifies workspace membership and role.
3. The handler uses the server-derived workspace id, never a trusted payload id.
4. Mutations that sync reads or collab depend on serialize through the change log.
5. Public share endpoints use `publicProcedure` with hashed tokens and a separate read-only shape.

## Data boundaries

| Boundary | Rule |
| --- | --- |
| Tenant | Every query with a workspace-scoped procedure includes `workspaceId`. |
| Page privacy | Private pages are filtered from sync snapshots and pulls for non-creators. |
| Local storage | One IndexedDB database per user id; the workspace is a partition key. |
| AI | Server-configured provider only; no arbitrary base URLs from users. |
| Public share | Hashed tokens, read-only payloads, outbound page links stripped. |
| Query console | Read-only transaction, workspace-bound views, no access to the base tables. |
| Plugins | Worker with no network or database access; every call checked against granted capabilities. |

## Query console

Settings → **Query** runs read-only SQL against the workspace. The base tables are
not reachable: the server keeps a `console` schema of views, each filtered by a
`lattice.workspace_id` setting bound for the duration of a transaction that is
opened `READ ONLY` with a statement timeout and a search path that excludes
`public`. Postgres itself then refuses writes, whatever the query says.

On top of that, a validator in the domain package rejects anything that is not a
single `SELECT` or `WITH`, blocks other schemas and system catalogs, and refuses
names that are not console views — after blanking comments and string bodies so
neither can hide a keyword. Results are capped at 500 rows and long cells are
truncated.

## Plugins

Settings → **Plugins** installs a manifest plus a source body that defines
`async function run(ctx)`. The plugin runs in a worker, and every API call it
makes is answered by the host, which checks the method against the capabilities
you granted. Enforcement is on the trusted side, so a plugin never decides what
it may do. A run is terminated after five seconds.

| Capability | What it allows |
| --- | --- |
| `page:read` | Read the open page's text and Markdown. |
| `page:write` | Replace the open page's body. Every write becomes a revision. |
| `page:create` | Create pages in the workspace. |
| `graph:read` | Read node and edge titles and relations. |
| `search:read` | Run workspace searches. |
| `ai:use` | Send prompts through the workspace AI configuration. |
| `storage` | Keep a small key/value store of its own. |

Capabilities are checked against what you granted, not what the manifest asked
for, so revoking one takes effect on the next run. A manifest that requests a
capability this host does not have is refused outright rather than quietly
trimmed — a plugin written for a more powerful host should not look installable.

### What the sandbox is, and is not

Before plugin code loads, the worker has its ambient powers removed: the network,
IndexedDB, caches, other workers, and dynamic script loading are all taken away.
Those globals are read-only accessors on the worker prototype, so they are
redefined rather than assigned — a plain assignment is silently ignored, which
would leave a plugin able to open the workspace database directly and go around
every capability check.

This is a containment boundary for a cooperative ecosystem, not a defence against
hostile code. Only install plugins you trust, which is why there is no plugin
directory and no remote install in this release.

Plugins are stored on the device, not synced, and there is no network capability
to request: a plugin cannot reach the internet because the capability does not
exist.

## Storage split

Page metadata and page bodies are intentionally separate:

- `Page` — title, icon, visibility, tree position.
- `PageDocument` — TipTap JSON, plain text, schema version, revision.

This keeps navigation lists light and gives document conflicts an explicit revision token. Canvas documents follow the same model.

See [Local-first sync](/docs/local-first-sync) for the mutation protocol.
